# Website form transaction ID release plan

This is a review candidate on `feature/form-transaction-id-live-baseline`, based on the canonical `baseline/live-site-2026-09-30` branch. No migration or deployment is authorized by this document. The serving Pages deployment at review time is `d0acd4af-738d-4dee-9f4b-5df4612bd4b0`.

The candidate adds a stable form `transaction_id` for Google Ads action `7152833432` while preserving Jobber intake if the new D1 transaction ledger fails. It also adds a read-only retraction preview; there is no retraction sender, scheduled job, or Google adjustment request.

1. **Preflight and runtime reconciliation.** Start from the current canonical branch. Run `npm ci`, `npm run check`, and `node scripts/check-live-site-baseline.mjs --check-live-deployment`. Review every entry in `scripts/live-site-reviewed-changes.json`. The baseline proves static bytes, but it does not independently prove the deployed Pages Function bundle. The current review candidate's `/api/leads` source predates the later 401 fencing, request-only retry, durable failed-lead queue, and failure alert present on `origin/main` at `956bf49`. Determine which Functions artifact is actually serving production and preserve every live intake protection before publishing an API bundle. **Do not deploy this candidate until that comparison and integration are complete.** Keep Cloudflare's automatic production and preview builds disabled.
2. **Back up and inspect D1.** Back up `good-attic-angi-jobber-router` (`934d7ad9-cba8-4cb4-9494-1e9980b7c403`). Check its schema and migration registry before applying only `migrations/0017_website_form_transaction_ids.sql`. The registry currently lists `0001`–`0009` although later qualified-phone tables exist, so do not run a blanket migration-directory apply. Verify the three new tables with read-only queries after the additive migration.
3. **Deploy the API first.** Prepare an API-only candidate containing the reviewed `/api/leads`, `/api/leads/conversion-signal`, and transaction modules, while retaining byte-identical current live static assets and the old active script. Verify that build and run the release guard before an explicitly approved Pages publish. Do not deploy this feature branch's complete `dist` for the API stage because it already contains the new form script.
4. **Verify intake before changing the browser.** With a controlled, authorized form submission, confirm a Request and Client in the correct Jobber account, the same transaction UUID in the API response and D1 row, and unchanged alert/attribution delivery. Check that a transaction-ledger failure still creates the Request and returns success. If this stage fails, restore the prior Pages Function artifact; leave the additive D1 tables in place pending review.
5. **Deploy the active script second.** Build from `src/site-interactions.js`. The reviewed candidate changes only the active script reference on 96 HTML pages, adds one content-addressed script, and adds its cache header. The old script remains available. Verify all other page bytes and the Utah, St. Louis, and Kansas City Quo numbers. After approved publication, confirm one successful form shows its thank-you, links the UUID to its Jobber Request, and invokes `DA - Submit Lead Form` with that `transaction_id`. A missing or mismatched API ID must still show success and invoke the conversion without an ID.
6. **Observe and retain rollback.** Watch form success, Jobber Requests, transaction reconciliation flags, conversion signals, and market routing. Restore the prior static asset bundle if the script stage fails while keeping the compatible API. No junk/duplicate retraction upload is enabled in this release.

The fail-open path covers the **new transaction ledger**. Jobber authorization still depends on D1, so a complete D1 outage can block intake; this release does not claim to solve that separate failure mode.

Tracking reconciliation is also required for two fail-open cases. A timed-out D1 reservation may finish after intake has continued; a background repair links or releases that row, and a failed background repair is logged for manual review. A retry after delivery became uncertain can create a second Request, recorded in `website_form_reconciliation_attempts`; staff must resolve which Request owns the conversion before any retraction preview treats that ID as verified. Neither case may block the customer-facing submission.
