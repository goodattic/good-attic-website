# Website form transaction identity and retraction preview

Migration `0017_website_form_transaction_ids.sql` is additive and is not part of `/initialize`. It is staged for review and has **not** been applied. The canonical live-site checkout has migration files through `0009`; the separate stage1-shadow checkout has `0010`–`0016`, and the live D1 migration registry currently lists only `0001`–`0009` even though qualified-phone tables exist. Do not run the entire canonical migration directory against production. Before applying `0017` individually, back up D1 and verify its live schema and existing table names. `website_form_conversions` covers Utah, St. Louis, Kansas City, and the existing general route.

With the proposed browser/API patch, a single browser-generated UUID is both the submission ID and the Google tag's `transaction_id`; the Request and Client IDs are attached after successful Jobber intake. A double-submit or reload-and-retry in the same browser tab reuses that UUID: the browser stores only a salted digest of the form contents and the UUID in session storage, with a 24-hour pending or 5-minute completed lifetime. If D1 tracking fails, Jobber intake proceeds. A reservation that completes after the fail-open timeout is reconciled in the background; a browser conversion signal arriving before that repair is retained. If a retry follows a possible Jobber write, intake also proceeds and flags the transaction for reconciliation; a duplicate Jobber Request may need staff cleanup. `conversion_state=client_signaled` means the browser invoked the Google tag, **not** that Google accepted the conversion. A lost browser acknowledgment can cause a repeat tag invocation with the same ID, which Google deduplicates for this action.

The proposed staff marker is a **Jobber Client tag**: `GAE:JUNK` or `GAE:DUPLICATE` when that Client has exactly one verified website Request. If the Client has more than one website Request, staff must use `GAE:JUNK:12345678` or `GAE:DUPLICATE:12345678`, with that Request's numeric ID. A plain tag requires a complete paginated Client Request read, including the target Request, and verified website/non-website provenance for every other Request. The reader must establish provenance from reliable source metadata or the attribution ledger; notes, archive status, and unknown sources do not count. If it cannot prove a sole website Request, the preview holds the plain tag and staff can use the Request-specific form. Jobber currently offers tags on Clients and does not offer Request custom fields. Apply only one disposition per Request. Archived or deleted status alone is never a marker.

`previewWebsiteFormRetractions` is a read-only shadow function for the three named markets; the general route is held. It is not wired into any route, cron, or Jobber reader. A future caller must supply a current Jobber read to verify the expected account, Request, Client, and the full Client tag list. For plain tags, `readJobberEvidence` must also supply `request.client.requests = {nodes, pageInfo:{hasNextPage:false}}`; each other node must have `source_verified:true` and `source:"website_form"` or `source:"non_website"`. It also requires a completed submission, a stored transaction ID, no pending transaction reconciliation, a browser conversion signal, and no prior retraction claim. It returns the exact proposed `RETRACTION` adjustment for Google Ads action `7152833432`, identified by `orderId=transaction_id`, or a hold reason. The output explicitly notes that browser signal does not prove Google acceptance. It sends no Google requests and writes no rows; a caller may supply a read-only Jobber lookup.

`website_form_retraction_outbox` is only a schema for a later sender. A future enabled sender must atomically claim the transaction ID before attempting `UploadConversionAdjustments` with `partialFailure=true`, inspect per-row failures, and fence ambiguous delivery; it must not automatically retry a possible successful submission. There is currently no scheduled job, route, or Google transport for retractions. No prior form conversion can be retracted by order ID unless that original conversion carried the same transaction ID.

Before enabling that sender, verify action `7152833432` is a `WEBPAGE` conversion and the original Google tag recorded the same transaction ID. Use Google Ads conversion adjustments (or its supported adjustment import), not the existing Data Manager API event transport: Data Manager does not provide a true count retraction. Google's current guidance is to wait at least 24 hours and submit within 54 days; hold events outside those bounds. Inspect Google's per-row `CONVERSION_NOT_FOUND`, `CONVERSION_EXPIRED`, and already-retracted results rather than treating a successful HTTP response as acceptance. A website retraction cannot be undone, so markers and request links must be verified before a sender is enabled.
