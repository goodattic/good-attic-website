# Quo call to operational Jobber Request lineage prototype

The first Quo call is preserved as the origin. The original Jobber Request can hold its call notes while staff schedule an assessment on a second Request. This prototype records a separate, audited link between those two Requests. It does not edit either Jobber Request or the website click attribution tables.

## Verification rule

1. Read the immutable `quo_call_attributions` row by `(account_id, quo_call_id)`. Require its original Request and Client IDs.
2. Query Jobber under that exact account for the original Request, its Client, and **the complete paginated Request history for that Client**. A partial or failed read is manual review.
3. Propose an operational Request only when it is on the same account and Client, was created within seven days of the call, and has an assessment, quote, or job. A phone or name match is never sufficient. A single candidate remains a proposal; multiple candidates are an ambiguity.
4. Have a reviewer confirm the exact Quo call, original Request, operational Request, and evidence reference. A multiple-candidate choice requires explicit acknowledgement of the ambiguity. The `call_request_lineage_links` insert is immutable; a trigger writes the confirmation to `call_request_lineage_reviews`. Proposals and ambiguities can also be written to that append-only review table. Later corrections use immutable `call_request_lineage_supersessions` decisions (migration 0023); consumers read only `call_request_lineage_active_links`.

The seven-day window is a conservative review threshold, not proof that two Requests are the same lead. Cases outside it require separate investigation. The current schema permits one call origin per original Request and one origin per operational Request in each Jobber account; conflicting links fail closed.

## Stage 3c shadow consumption

Migration `0018_call_origin_stage3c_shadow.sql` adds a separate `call_origin_shadow_events` ledger. An opt-in `CALL_ORIGIN_SHADOW_ENABLED=true` hook in Stage 3c's `processObject` observes Request, Quote, and Job objects without changing its website click outcome path. The hook is disabled by default. It re-reads the operational Request under the exact Jobber account and Client. A direct original Request or a verified lineage link can then resolve to the original Quo call. For a verified link, it also re-reads the original Request and checks the Quo call row against the stored source identity. Missing relationships, account/Client conflicts, and multiple call origins hold; phone and name matches are never used.

The shadow ledger uses deterministic call, active decision, Request, milestone, and object IDs and stores both original and operational Request IDs. It records first observed booking time (when Stage 3c has one), assessment completion time, quote approval time, and job creation time. Reprocessing cannot insert the same event twice. Missing milestone times produce no event. For a job carrying an approved quote, the quote approval event deduplicates against the Quote observation; the job creation event retains the actual Job ID. These records contain no Google click IDs, conversion actions, values, or upload state. They never enter `closed_loop_stage1_leads` or the Google outbox.

Migration `0022_call_origin_shadow_replay.sql` adds a checkpoint for cached Request/Quote/Job observations. Stage 3c selects at most 25 call-origin cached objects per tick when a direct call or active verified link is present and the source timestamp, first scheduled time, or active decision differs from the checkpoint. A resolved unchanged object makes no further authoritative Jobber Request read; a held object is retried after one hour. A newly verified link replays an already scanned Request, and a later source update replays it again. The existing website selection and outcome path are unchanged. The SQL selector still scans the local cached object table each tick, so its D1 query cost should be measured before enabling the flag on a large history.

Use `call_origin_shadow_current_events` for current call-origin evidence. It joins each verified event to the active decision and operational Request; an original-Request event is current only while no verified link exists for that call. On supersession, earlier rows remain in the audit table but immediately disappear from this view. The corrected Request must be observed before new current milestone rows appear. A direct Quo original Request cannot resolve as the operational Request while its active verified link points elsewhere. Website and Google accepted events are not changed by this shadow view.

The code and migrations have only been exercised in isolated tests. Migrations 0017, 0018, 0020, 0022, and 0023 have not been applied to production; the feature flags are not enabled. Before a live shadow run, apply the migrations in order, exercise the authenticated review workflow, measure local cache query volume and additional Jobber reads, add durable held-reason metrics/retries, and reconcile one market against Jobber manually. The current hook logs a static error if its separate shadow write fails so the website pipeline continues; that is insufficient production observability. The cached replay can re-evaluate an existing assessment/quote/job observation after a verified link or later source update without changing its website upload state. A Jobber relationship change that produces no source update and no reviewed lineage correction will not trigger this cache replay on its own.

## Google call evidence shadow

Migration `0020_google_call_match_shadow.sql` adds a separate Google `call_view` evidence ledger and append-only check history. The scheduled worker invokes `googleCallMatchShadowCycle` only when `GOOGLE_CALL_MATCH_SHADOW_ENABLED=true`; it has its own three-hour run claim and fourteen-day lookback. This path reads Google calls and Quo call-attribution rows but never calls the qualified-phone upload function. It includes calls at or above sixty seconds, which the qualified-phone uploader deliberately excludes. Each row retains the Google resource, campaign ID/name, call time, duration/status, area code, and a Quo call ID only when the existing market + area code + 120-second time matcher returns exactly one Quo call. A second Quo call with the same caller or a second Google call for the same Quo call leaves the evidence held with an explicit reason. Later conflicting Google evidence demotes a prior match and records both checks. Full caller phone is not stored in this ledger.

A unique match is **call evidence, not conversion eligibility**. The matcher uses area code and time, so a nearby unrelated caller with the same area code can still be a false positive. Any later call-origin conversion must additionally verify the original Quo call, Jobber account and Client, operational Request lineage, milestone, and Google action rules. The shadow ledger has no click ID, conversion action, or upload state. Older calls outside the fourteen-day scheduled lookback require a controlled backfill. Migration 0020 has not been applied and the flag remains off.

Stage 3c currently uploads website click outcomes and a separate qualified-phone call conversion. It does not upload call-origin assessment, quote, job, invoice, or payment milestones. Invoice and payment source relationships still need authoritative Jobber reads. Google action mapping, call-origin conversion eligibility, consent handling, values, and idempotent upload gates need a separate reviewed design. Accepted Google events must remain immutable and must never be replayed simply because a lineage link was added later.
